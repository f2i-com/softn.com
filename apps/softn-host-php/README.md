# SoftN PHP on-demand WASM runtime (preview)

An application-independent host for SoftN server API v1. Apache/PHP starts one runner process per request: softn-runner (`bin/softn-runner-linux-x86_64`, a release's backend carries it; below) or, without it, the bundled Node with `runner.mjs`. ZIPP's safe-sandbox WebAssembly interpreter evaluates the application's server logic; the runner provides explicitly granted host capabilities and SQLite. There is no daemon, listening backend port, PHP FFI, or PHP WASM extension.

## Deployment

Linux x86-64 (glibc 2.28+ where requests run on the bundled Node; softn-runner is static), PHP 8.1+, enabled proc_open/proc_get_status/proc_terminate/proc_close, executable-file permission, Apache mod_rewrite. The host itself needs no PHP extension a stock PHP lacks; PHP GD enables the photo adapter (Debian/Ubuntu: the `php-gd` package, which a stock install does not include; without it `/api/meta` reports `photos:false` and a photo route answers `503` with `diagnostic:"php_gd"`). Put webroot/ contents in the existing DocumentRoot and backend/ outside all public directories. The API is served at the site's root: `/api/...` is matched from the start of the URL, so a site installed in a subdirectory (`/shop/api/...`) answers 404 for its routes. api.php defaults to a sibling backend directory; edit its absolute path if necessary. Allow the supplied .htaccess FileInfo/Options/Indexes/AuthConfig directives (or AllowOverride All) and retain the site's PHP handler. Without mod_rewrite the app itself still loads and `/api/...` is Apache's own 404 (the rules ask for the module; it used to be a 500 for every request). Remove any old /api/ reverse proxy. Run `php backend/setup.php` as the PHP service account, which must own the backend folder. Setup creates private config/data; it does not start a service. It then checks what the first request would otherwise find out: the PHP version and process functions, GD when the app takes photo uploads, that the runner a request starts is there and runs on this machine (softn-runner where the backend carries it, else the bundled `bin/node`; neither runs on ARM or from a `noexec` mount, and Node needs glibc), and, with an application installed, that `/api/meta` answers — started as a request's runner is, and applying the app's pending migrations, so run setup as the PHP account, never root (as root it stops before that check, which would run an app's code with root's rights and leave the database root's). Each problem is printed as a `WARNING:` line and setup exits 1; when the app does not start, the line carries the runner's own reason after the stage label (`application_identity ... It said: softn: startup stage application_identity: Operator configuration belongs to another app`). What setup cannot go on from is one line saying what to do and exit 1, not a PHP error: a folder the account may not write in, a manifest that is not JSON, half an upload. Setup runs under the command-line PHP, whose `php.ini` is often not the web server's (other `disable_functions`, other extensions, sometimes another PHP altogether): it says so, and `/api/meta` through the site is the check of the one that serves requests. It also says which runner requests run on. No system Node is needed or used.

## softn-runner: requests without Node

A release's backend carries softn-runner (`apps/softn-runner`) in `bin/softn-runner-linux-x86_64`, a static Linux x86-64 program, with its licences in `licenses/SOFTN-RUNNER-THIRD-PARTY-LICENSES.txt`. Where it is there and the server is Linux x86-64, every request is started on it instead of Node: it takes the request `runner.mjs` takes, on stdin, and gives the same answer and the same line in PHP's error log, with the app's logic in a wasmtime instance that has the clock and randomness and nothing else. A request is answered in about a third of Node's time: 57 ms against 170 at the median, for a request whose handler only answers, through php-cgi and http.php, on one Linux machine (WSL, PHP 8.3, 40 requests each). The server needs no Node for requests at all. `request.php` `softn_runner_choice` is the rule, for http.php and setup's check alike.

Node and `runner.mjs` still answer:

- where `private/config.json` says `"runner": "node"` (the operator's choice; remove it, or write `"auto"`, to go back; `"requestMemoryMb"`, below, is softn-runner's alone);
- where `enableRequestHook` or `enableAfterRequestHook` is `true`: those hooks are JavaScript modules of the operator's (`operator/`), which only Node runs, and softn-runner refuses such a configuration;
- where the backend has no softn-runner (an archive built without `--runner-dir`, or one from before it), or the server is not Linux x86-64.

`bin/node` stays in the backend for those, and for the WebSocket bridge (`LIVE_UPDATES.md`), which runs on Node. Where softn-runner differs from Node's runner is in its README: a frame of its own shim is named `zipp:preamble`; `softn.time.format` ends before JavaScript's dates do (more than 262,000 years from year 0); its SQLite is the one it carries (3.53.2), and keeps temporary data in memory; and a request still running a quarter of a second before the 20-second deadline is stopped, rolled back and answered (`500 host_error`), where Node's runner was killed and PHP answered `503 runner_unavailable`. On Linux softn-runner also locks its own process down before every request, with the kernel's Landlock and seccomp (no root, container or setup step: a process may always restrict itself): it can read the backend folder and make, write and remove regular files only in `private/data` and `private/limited`, and cannot run a program, make a process, open a socket, signal or reach another process, change a file's mode or owner by path, or make a link or device. Setup tries each of those and says what this kernel refused, and anything it did not; a kernel without Landlock (before 5.13, or with it switched off) is a NOTE, which also says that other processes of this account then stay reachable through `/proc`, and the rest still holds (`apps/softn-runner/README.md`, The process's own lockdown). How much memory a request may take is the operator's: `"requestMemoryMb"` in `private/config.json`, a whole number of MiB from 128 to 1024, and 256 without it, what Node's copy of the engine is held to here. The app's engine may grow to that, a script's heap to 64 MiB less (512 MiB at most; past it the engine stops the script and the request fails, `500 host_error`, the log saying "script exceeded its memory budget"), and SQLite to that again (Node's `node:sqlite` has no limit, and spills to temporary files). Setup says what a request may take, and warns of a value it does not take; `BUILD-INFO.json` records the setting (`softnRunner`). With four to sixteen requests at once, size the server for it, or lower `"workers"`. What a request does take is far less: about 15 MB for a handler that answers and writes a row, where Node's runner takes about 100 MB, because the engine's compiled code is used where it lies in the program, shared by every request running (`apps/softn-runner/README.md`, Memory, has the figures).

What the web server's PHP must allow, beside the functions above: `open_basedir`, where the host sets it, has to include the backend directory (`api.php` answers `503` with `diagnostic:"open_basedir"` when it does not; it used to print the paths on a host that shows errors, and to say the backend was not found); `post_max_size` at least the largest body a route takes (5.6 MB for a photo route; PHP's default is 8M); `memory_limit` is raised to 256M by http.php itself where `ini_set` is allowed. `api.php` answers `503` with `diagnostic:"php_version"` on PHP older than 8.1 and `diagnostic:"backend_path"` when `$backend` is wrong, instead of a PHP error that would print server paths. http.php's own refusals, in the order it finds them: `php_process_functions`, `backend_public` (the backend is inside the document root or beside `api.php`: move it, before setup makes a key and a database there), `private_permissions` (`private/` belongs to another account than the web server's PHP: setup was run as root or as another user), `setup_required`.

Low-level template archives contain no application. The optional-backend single-app distribution includes the public counter example, but no private server bundle. Install the expanded private bundle at backend/app/, place the public .softn at webroot/app.softn, and supply a matching runtime.config.json before setup. Prefer the packager to generate the client hash and validate separation automatically:

```
node apps/softn-host-php/package.mjs --runtime <compiled-single-runtime> --bundle <expanded-private-bundle> --client <public.softn> --node-dir <node-linux-x64> --wasm-dir <zipp-web-artifacts> --notices <native-notices> --out <hosting.zip>
```

Use `--template` without --bundle/--client to produce a reusable runtime archive. Build tools are needed only on the packaging machine. Hosts receive compiled assets and a bundled executable.

For a site-owner-approved application, pass `--preapprove-permissions` with a current single-app frontend build. This writes `permissionMode:"preapproved"` into the public runtime.config.json and pins the bundle SHA-256. The single-app shell immediately enables only the bundle's declared permissions and hides its consent banner; browser file pickers and camera/microphone permission prompts remain browser-controlled. Default deployments still prompt. This is an operator setting in the deployment config, not a self-approval flag inside an app bundle. Older frontend builds must be replaced before using this setting.

## Supported contract

Optional read-only polling routes and the separately started WebSocket bridge are
documented in [LIVE_UPDATES.md](LIVE_UPDATES.md). The single-app CI distribution
includes both; polling requires no persistent service. The static-only ZIP remains
available without backend files.

- manifest.server.entry selects the private .logic source, and is required: this host has no default (without it the app does not start, `Invalid bundle path`), and reads no `server.scripts`, where the Rust host reads `server/main.logic` when the entry is left out and appends the `server.scripts` files after it. manifest.server.routes selects handler functions, with the route schema the Rust host reads (`apps/softn-host-rust/PRIVATE_BACKEND.md`): `method`, `path`, `handler`, optional `transaction` (`read` or `write`; unset or `none` means `read` for a GET and `write` otherwise — the Rust host does the same for an app with a private database, and runs every route of an app without one with no transaction, ignoring a declared one with a warning), optional `authorization` (`application` or `anonymous`; unset means `application` here, but the Rust host refuses to start an API v1 app with a route that leaves it out, so a bundle meant for both writes it on every route), optional `maxBodySize`. A route this host cannot serve — a path outside `/api/` (Apache routes only those to api.php), a method other than GET/POST/PUT/DELETE, or `authorization: "host-token"` (the Rust spelling; `hosttoken` is also read; this host holds no token, so such a route answers 401) — is set aside and listed under `unservedRoutes` by `GET /api/meta`, and the rest of the app runs. No route parameters or wildcards yet. A path nobody declared is `404`; a declared path asked with a method it does not declare is `405 method_not_allowed` with `Allow` (it used to be 404); `HEAD` on a GET route is that GET with the body left off, and the handler is told the method is `GET` (it used to be refused, 405). All three as on the Rust host.
- Request bodies are JSON objects (`application/json`, nesting 62 levels deep with the body itself the first, which is as deep as a handler can be handed: one level more is `400 invalid_request` on both hosts, where it used to reach the handler here as `null`), limited to the smaller of the route's `maxBodySize` and `config.server.maxBodySize`, else 256 KB; a declared value is honoured up to 2 MB (a `photo` upload route up to 5.6 MB). The Rust host bounds a route by the same two fields with a 2 MB default. No body reaches the handler as `{}`. Refusals carry the Rust host's codes: `413 payload_too_large`, `415 unsupported_media_type`, `400 invalid_request`, `405 method_not_allowed`, and `404 not_found` for a path no route declares (which had no code here).
- The handler receives `{method, path, query, headers, body}` as on the Rust host: `query` maps each percent-decoded name to its last value, always a string (PHP's own `$_GET` renaming and arrays are not used); `headers` holds every request header, lower-cased, except `Cookie` and `Proxy-Authorization`, with `authorization` and `idempotency-key` always present (empty when not sent). The handler's `body` is sent to the client exactly as the runner serialised it; PHP never decodes and re-encodes it.
- A browser page on the site itself may call its API; any other page's origin must be listed in `config.server.allowedOrigins` (exact `scheme://host[:port]`), or the request is `403 origin_not_allowed`. The site's scheme is the connection's, or a `trustedProxies` peer's `X-Forwarded-Proto`. Requests without `Origin` (non-browser clients) are not checked: authentication is the app's bearer session, never a cookie, so there is no CSRF surface. `OPTIONS` always gets an ok status and never reaches a handler (`204` here, `200` from the Rust host's CORS layer): an allowed Origin gets `Access-Control-Allow-Origin`, a foreign one does not (its browser stops at the preflight), and one with no Origin is not a CORS preflight and learns only the methods.
- Requires server API v1. Implemented capabilities: sql, crypto, time, trusted-client-ip, transaction-scope, photos. Requested capabilities must also be granted in private/config.json. Unsupported capabilities and enabled XDB sync fail closed; apps requiring db/XDB sync, arbitrary HTTP/FS, native modules or persistent callbacks are not compatible with this first adapter.
- The app owns authentication/authorization for `application` routes. Request headers reach it as data; the host itself trusts only what it derives (the client address, the sanitised upload). The client address (the host's per-address rate limit, `429 rate_limited` with `Retry-After` past it — 120 requests a minute unless the manifest's `config.server.requestsPerMinute` says otherwise, 0 for none, as on the Rust host; an IPv6 client shares its /64; once the runner has refused a bucket it leaves a note in `private/limited/`, and PHP answers the rest of that minute's requests from it without reading the body, taking a worker slot, decoding a photo or starting Node; an upload the host refuses is counted like any other request, where it used to be answered before anything counted it — and `req.client_ip` for an app granted trusted-client-ip) is REMOTE_ADDR, and X-Forwarded-For is ignored — so behind a CDN or reverse proxy every visitor shares the proxy's address and one rate-limit bucket. To fix that, list the proxy's addresses or CIDR ranges (IPv4 and IPv6) as `"trustedProxies": ["10.0.0.5", "173.245.48.0/20"]` in private/config.json: X-Forwarded-For is then read only when the connecting peer is listed, and walked from the right past every listed hop to the first address that is not one, so a client cannot choose its identity (the Rust host's `--trusted-proxy=<peers>` rule). List only addresses your proxy connects from; `0.0.0.0/0` would let any client name itself. Apache mod_remoteip, which rewrites REMOTE_ADDR before PHP sees it, remains an alternative.
- `/api/meta` is host-reserved and returns app ID/version, development mode, photo availability and runtime identity. `softn.config` contains manifest.config.app under two flags the host sets, `development` (the operator's) and `photos` (the capability granted and GD loaded, as `/api/meta` reports it); an app key of either name is replaced, as on the Rust host. A photo upload is turned the way its EXIF orientation says before the handler sees it (JPEG; the copies handed on carry no EXIF). Optional onStart() runs inside each fresh request VM, and so for every request, inside its transaction; the Rust host runs it once when the app is loaded, outside any transaction, and discards the globals it set. Write it to check what it needs and to leave nothing in memory a request depends on, and both run it alike.
- One host call (`softn.sql.*`, `softn.crypto.*`) carries up to 2 MiB of arguments beside its statement, as on the Rust host, and a response may be 3 MiB. A request body reaches the handler as the text it was: PHP checks it (a JSON object, the depth and number range above) and hands the client's own bytes to the runner, never a decoded copy written again. A non-ASCII body is not inflated on its way, and neither is one of numbers: PHP spells `1e16` as `1.0e+16`, so a 2 MiB body of them was 7.5 MB by the time the runner measured it, past the 6 MB it reads, and was answered `503 runner_unavailable` uncounted by the rate limit. `-0` reaches the handler as `-0`, as on the Rust host (written again by PHP it was `0`).
- Two differences from the Rust host a handler can meet: there is no `softn.media` here (a photo reaches a handler only through an `upload: "photo"` route, already sanitised), and no document store (`db.*`).
- A request is one transaction, committed after the response has been validated. A thrown handler, an invalid response or a host call that failed rolls it back and answers `500 host_error`, and that includes a failed call the handler caught: what it wrote before the failure is not kept. A handler that expects a statement to fail and wants its own answer returns `rollback:true` with it. What it catches says why: `e.message` is the host's reason (`That local time does not exist during daylight saving. Choose another time.`, `Only one SQL statement is allowed`), or for a statement SQLite itself refused `SQL write failed` / `SQL query failed`, whose detail stays in the log. It used to be `host bridge call failed` whatever had failed. An error response with no failed call commits, so a wrong guess keeps its attempt counter. This is the Rust host's rule.
- SQL uses the declared private-sqlite migrations, applied in one transaction in sorted path order (as the Rust host), each recorded with its SHA-256. A changed, duplicated, or previously applied but no longer listed migration stops startup (`diagnostic:"database_migrations"`). App tables must not begin with `_` (host-reserved). Lock waits are three seconds; past that the answer is the retryable `503 database_busy`, as when every process slot stays taken (below). The SQL rules are the Rust host's (`runtime/sql.mjs`; its `bridges/sql.rs`), case by case in `tests/sql-parity.json`. Migrations may create and drop the app's tables and indexes, `ALTER TABLE` (add, rename and drop columns, rename tables), use CTEs (also recursive), the date functions and `printf`/`format`; attached DBs, PRAGMA, transaction control, views, triggers, virtual and temp tables, and `_` names (including renames into the namespace and `_` index names) are denied. Adding a column to a STRICT table, or a column with a CHECK, makes SQLite check the table with an internal `quick_check`, which is a PRAGMA: for that one statement this host lets the check through when the statement is exactly `ALTER TABLE [main.]t ADD [COLUMN] c TEXT`, optionally `REFERENCES` one column of another app table (no other type, no NOT NULL, DEFAULT, CHECK, UNIQUE or COLLATE), and any other such ADD fails. A migration file with a NUL, or with a quote or comment left open, is refused before any of it runs (`runtime/migrations.mjs`). At request time, query/first run one read-only statement (SELECT, WITH, VALUES) and execute one INSERT, UPDATE, DELETE or REPLACE (optionally behind WITH) that returns no rows, only in a write route. One statement (a `;` in a literal or comment is text); exactly as many parameters as the statement takes, at most 100, each a string, null or number within ±2^53−1 (a whole number binds as an INTEGER, as on the Rust host); 1000 result rows, 2 MiB result bytes, no BLOB values. The connection has those of the Rust host's SQLite limits that only refuse a new statement (`SQL_LIMITS` in `runtime/sql.mjs`): no attached database, 100 parameters, 100,000 opcodes. The opcode count is a request's: a migration is not held to it on this host, because one INSERT of fifteen thousand seed rows compiles to more and this host has always applied one (held to it, an app that ships such a list did not start on a fresh install, and the log said `out of memory`). The Rust host does hold a migration to it, so an app for both hosts writes a long seed list as INSERTs of a few thousand rows each. The Rust host also holds a value, string or row to 2 MiB, a table to 200 columns and an expression to 100 levels deep, and this host does not, because a database that already has a longer value, a wider table or a deeper CHECK would become unreadable; an app for both hosts should stay within them. None of these bounds memory or time: SQLite here takes `PRAGMA hard_heap_limit` without enforcing it, and a long query is stopped only by the runner's deadline. `execute` answers `{changes, lastInsertRowid}`, and `lastInsertRowid` is the id of a row that statement inserted, 0 when it inserted none (an ignored `INSERT OR IGNORE`, an upsert that updated, an `UPDATE`, a `DELETE`), on both hosts: it used to be whatever the connection had last inserted, the host's own rate-limit row included. A row's columns, and every object the handler is handed or returns, keep their order on both hosts. Functions: count, min, max, sum, avg, total, coalesce, ifnull, nullif, length, lower, upper, trim, ltrim, rtrim, substr, substring, replace, instr, abs, round, like, glob, typeof, unicode, char, hex, quote; the SQLite authorizer refuses every other function and the host's tables. The Rust host refuses that STRICT-table ADD, as it refuses the check (the `rust` notes in the fixture); an app for both hosts should not add a column to a STRICT table in a migration.
- `crypto` provides sha256, hmac, randomHex, randomInt, equal and seal. Key bytes and unseal are unavailable to the guest. Domains are configured per app in private/config.json. `randomInt(bound)` and `randomHex(bytes)` take a whole number or text that spells one (`req.query.sides`), the bound up to 2^53-1 and the bytes from 1 to 64 (anything else throws), as on the Rust host (`tests/crypto-parity.json`); a bound had to be a number under 2^48. `time` provides now, parseZoned, format and age using IANA zones in any case, or an offset from UTC (`+10:00`, `+1000`, `+10`); `age` with no zone, a null one or an empty one is UTC. `format(seconds, zone)` writes `Thu, 1 Jan, 11:00 pm · Melbourne` (the last part of the zone as the caller spelt it), from word lists both hosts keep, so the text no longer follows the locale data of whichever Node runs it. Both hosts are held to one list of calls, `tests/time-parity.json`. Calendar parsing rejects ambiguous/nonexistent local times and supports minute-resolution offsets.
- A route with `upload:"photo"` requests the trusted PHP/GD upload adapter, which accepts a data_url, re-encodes it and supplies req.upload. Require the photos capability for these routes. No other request may inject req.upload. A photo the host will not take is `400` with `code: "photo_rejected"`, as on the Rust host, answered by the runner once it has counted the request against the rate limit. What a photo is, is read from its bytes (the label only has to be one of the three types), a PNG is animated when it has an `acTL` chunk before its image data (not when those four bytes turn up anywhere in the file), and transparency is painted white; the Rust host does the same three.

## Security checklist

- `backend/` outside every public directory and Alias (http.php refuses to run when the backend is inside the document root, inside the directory an Alias or a user directory maps to, or in or below the directory `api.php` is in, and says so, `backend_public`, before it says anything about setup; the packaged `backend/.htaccess` denies all as a second guard).
- `private/` and `private/data/` are `0700`, `config.json` `0600`, owned by the PHP account; setup sets these. Never publish or commit them.
- `display_errors` off (api.php and http.php set it for their own requests where the host allows `ini_set`, api.php before it looks at any path; a host that disables `ini_set` must have it off itself).
- Check it from outside, once the site is up. Each of these must answer 403 or 404, never 200:

  ```
  for path in backend/private/config.json backend/private/data/application.sqlite backend/app/manifest.json backend/runner.mjs .htaccess; do
    curl -s -o /dev/null -w "%{http_code} /$path\n" "https://your.site/$path"
  done
  curl -s https://your.site/api/meta     # {"development":false,...,"runtime":"zipp-wasm-on-demand",...}
  ```

  What stands between a visitor and the private files (run against Apache 2.4 with the packaged archive; nginx reasoned from it, since it reads no `.htaccess`):

  | Layout | Apache, `.htaccess` read | Apache `AllowOverride None`, or nginx |
  | --- | --- | --- |
  | `backend/` beside the document root (as documented) | no URL names it: 404 | no URL names it: 404 (and `/api/` is not routed until the server is told to, below) |
  | `backend/` under the document root (the whole archive unpacked there, say) | 403 for everything under `backend/` (its deny-all `.htaccess`) | **200**: the database, `config.json` with the key, the server manifest, logic and migrations, and the runner's sources are plain downloads; `http.php` and `setup.php` answer 404 where PHP runs them. Only where the web server runs as another account than PHP do the `0700`/`0600` modes still keep `private/` shut |

  So on a server that does not read `.htaccess`, the layout is the only protection. Where a request still reaches `api.php` with the backend in a public place, the host refuses it (`backend_public`), and that is the sign to look for; it cannot stop the web server handing out files that have a URL.
- `config.server.allowedOrigins` lists only origins other than the site itself that must call the API; `trustedProxies` lists only your own proxy/CDN ranges.
- `capabilities` in private/config.json grant only what the app declares; leave `enableRequestHook`, `enableAfterRequestHook` and `enableHostContext` off unless you installed trusted operator code.
- The webroot `.htaccess` sends `X-Content-Type-Options`, `Referrer-Policy`, the cross-origin isolation headers (`Cross-Origin-Opener-Policy`, `Cross-Origin-Embedder-Policy`) and framing limits (`frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN`); to embed the app on another site, list that origin in `frame-ancestors` and drop `X-Frame-Options`. API responses carry `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.
- Keep PHP, the bundled runners (softn-runner and Node) and ZIPP patched: replace the backend runtime files from a new release (below).

## Backup, restore and upgrade

Back up `backend/private/` as a whole: `config.json` (its `keyHex` and `cryptoDomains` decrypt sealed data and verify HMACs; losing it loses them) and `data/application.sqlite` with its `-wal`/`-shm` files. For a consistent copy while serving, use SQLite's backup API (`sqlite3 application.sqlite ".backup /safe/place.sqlite"`) or stop requests first; copying only the main file while WAL holds commits can lose them. Restore by putting both back, owned by the PHP account with the modes above.

To upgrade, keep `backend/private/`, `backend/app/` (unless deploying a new app version) and your edited `api.php`; replace all the other backend files together (http.php, request.php and the runners change as one) and the webroot runtime from the new archive, then run setup again (it preserves settings, makes the runners executable again, and re-runs its checks). A backend upgraded to an archive that carries softn-runner answers on it from then on (setup says so); `"runner": "node"` in `private/config.json` keeps Node. A new app version may add migrations; never edit or remove one that has been applied. Upgrading to this runtime: migrations now run in sorted order and a deployment that dropped an applied migration from its manifest stops at `database_migrations` until it is listed again; the webroot `.htaccess` now limits framing. `api.php` itself changed in this release (it no longer prints paths under `open_basedir`): take the new file and set its `$backend` line again, do not keep the old file.

## Nginx

Nginx does not read `.htaccess`, and neither does an Apache with `AllowOverride None`: every rule the archive ships in one has to be written into the server's own configuration, and nothing in `backend/.htaccess` protects a backend that was put under the document root. The equivalent, inside the site's `server { }`, with PHP-FPM (reasoned from the Apache rules and nginx's documented behaviour, not run in the test suite: check it as the security checklist says):

```nginx
root /srv/site/webroot;            # backend/ lives outside it, e.g. /srv/site/backend
index index.html;
# Dot files, as Apache's FilesMatch "^\." refuses them; /.well-known/ stays
# served, so a certbot --webroot renewal still finds its challenge.
location ~ /\.(?!well-known(?:/|$)) { deny all; }
location = /api.php { return 404; }
# A second guard, as backend/.htaccess is on Apache: nothing of these is served
# even if someone uploads them into the document root.
location ~ ^/(backend|private)(/|$) { return 404; }
location ^~ /api/ {
    # The largest body the runtime takes is a photo upload (5.6 MB); nginx's
    # own default of 1m answered most of them with its HTML 413.
    client_max_body_size 6m;
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $document_root/api.php;
    fastcgi_param HTTP_AUTHORIZATION $http_authorization;
    fastcgi_pass unix:/run/php/php-fpm.sock;
}
add_header X-Content-Type-Options nosniff always;
# Cross-origin isolation, as the .htaccess sends it: without it the page has
# no SharedArrayBuffer, and an app on the CPU language-model provider runs on
# one core.
add_header Cross-Origin-Opener-Policy same-origin always;
add_header Cross-Origin-Embedder-Policy credentialless always;
add_header Content-Security-Policy "frame-ancestors 'self'" always;
add_header X-Frame-Options SAMEORIGIN always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
# The app, its settings and its bundle are asked for again on every visit.
# add_header in a location replaces the server's, so they are repeated.
location ~ ^/(index\.html|runtime\.config\.json|app\.softn)$ {
    add_header Cache-Control no-cache;
    add_header X-Content-Type-Options nosniff always;
    add_header Cross-Origin-Opener-Policy same-origin always;
    add_header Cross-Origin-Embedder-Policy credentialless always;
    add_header Content-Security-Policy "frame-ancestors 'self'" always;
    add_header X-Frame-Options SAMEORIGIN always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;
}
# A types block replaces the table inherited from http { }: without the
# include, .html, .css and .js would all be sent as the default type.
include mime.types;
types { application/wasm wasm; text/javascript mjs; }
```

The block used to end with the `types { }` line alone, which, pasted into a `server { }`, leaves every other file without its type. It also left out `X-Frame-Options`, `Referrer-Policy` and the `no-cache` rule the `.htaccess` sends, so a visitor could go on running an old app after an update, and the two cross-origin isolation headers (`Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: credentialless`), so an app on the CPU language-model provider ran on one core. Nginx warns of a `duplicate extension` where its own `mime.types` already lists `wasm` or `mjs`; that is harmless. Stock `fastcgi_params` passes `HTTPS`, `REQUEST_SCHEME` and `DOCUMENT_ROOT`; a custom one must pass the first two, or same-site HTTPS pages look like `http://` and are refused as `origin_not_allowed`. Directory listing is off by default in nginx. `php -S` is not a supported server: it neither routes `/api/` nor honours `.htaccess`.

## Isolation and operation

Guest logic has no Node/PHP objects or filesystem/network/environment access, and no timers: `setTimeout`, `setInterval`, `clearTimeout` and `clearInterval` throw an Error saying so, as on the Rust host, because nothing runs after a handler returns. The only synchronous bridge is an exact capability dispatcher. Each VM has 5 million instructions and 512 host calls. The packaged linear-memory maximum is reduced from the upstream 1 GiB to 256 MiB, for Node's runner; softn-runner holds its engine to `"requestMemoryMb"`, 256 MiB unless the operator says otherwise (above). PHP enforces a 25-second child deadline, bounded pipes, and `config.server.workers` concurrent slots (four when unset, at most sixteen, and no more than `"workers"` in `private/config.json` when the operator sets it there: the manifest is the app owner's); a request that finds them all taken waits for one, up to a second and a half, while fewer than two others are waiting already (below; under php-fpm only where the operator has said how many may), and is otherwise a `503 database_busy` to retry. Node managed heap is capped at 128 MiB separately; these are not total RSS limits. SQLite operations are transactional and a killed process rolls back uncommitted writes. The host rate limit persists across requests; quotas are per installed application. Separate installations/config keys/databases are required for separate tenants.

On Node's runner (where softn-runner is not used: above), a request is a Node process, and what that costs is mostly not the handler. Measured on one Linux machine with Node 24.21 and PHP 8.3 (a request whose handler only answers, through php-cgi, the median of 40): 0.17 s. Of that, PHP is about 12 ms, Node and its worker thread starting about 70, the engine being compiled as it first runs about 45, the handler 4, and SQLite waiting for the disk between 20 and 85 from one run to the next (the rate-limit count is a committed write on every request, and the last connection to close checkpoints the log; on memory-backed storage the same request took 0.15 s). The runner is started with `--no-wasm-tier-up --no-wasm-dynamic-tiering`, V8's optimizing compiler kept off the engine: left on, V8 starts optimizing the engine's dispatch loop while the handler runs, a compile of about 450 ms and 100 MB that no request lives long enough to use, and a process cannot end while it runs. The same request then took 0.53 s, four times the processor time (0.64 s against 0.15 s) and twice the memory at its peak (210 MB against 110 MB), all of the difference after its answer had been written; the heaviest handler the instruction budget allows was no faster for the optimizer either (0.53 s against 0.19 s), and neither was a 2 MiB body of numbers or strings read and sent back (0.55 s against 0.26 s). The optimizer does pay for itself once a request runs past about three quarters of a second, which takes moving a great deal of data through the engine: 2 MiB of small objects in and out again took 0.75 s without it against 0.68 s with it, a handler that reads 1.7 MB of rows a hundred times 0.99 s against 0.83 s, and one that does so five hundred times (about the most host calls a request may make) 4.0 s against 3.3 s. That is the price of the flags, and it stays far inside the runner's 20-second deadline. A tiering budget between the two (`--wasm-tiering-budget`) was tried and is worse than either: whichever request crosses it near its end waits for the compile. `softn_runner_command` in request.php is where the command is written, for http.php and for setup's check alike. softn-runner has none of this: its engine is compiled ahead of time, into the program.

A request that finds every worker slot taken waits for one, briefly, before it is told the server is busy: up to a second and a half (`SOFTN_SLOT_WAIT_MS` in request.php), trying again every 5 to 15 ms, and only while fewer are waiting already than may: half as many as there are workers, two for the default four, or `"slotWaiters": N` in private/config.json (0 for none). Under php-fpm none may until that setting is written (below). A request past that is refused at once, as every request past the slots used to be: a page that made six calls as it loaded got `503 database_busy` for two of them on the default four workers, with a slot a fifth of a second from free. Measured on the same machine, requests made together: of five, twelve and forty, four each were answered and the rest refused within 15 to 45 ms; now five of five and six of six are answered (the slowest in a third of a second), and six of twelve and of forty, the rest refused at once. With `"slotWaiters": 8`, twelve of twelve and of forty (0.6 s). The wait holds no lock and starts nothing: a waiting request has a place, an empty file in `private/waiting/` that is counted and never locked, and each try opens the slot files, asks without blocking and closes them. It comes after everything that is refused without a runner (another site's origin, an undeclared path or method, a bucket over its rate limit, a body too large or not JSON), so those are answered as fast as before, and before a photo is decoded. A request that gives up was never counted against the rate limit, as it was not before; one whose bucket was refused while it waited is answered `429` when its turn comes, without a runner.

How many may wait is the bound that matters, and it is the operator's to set because of what waits with a request: one of the web server's PHP workers, of which a server has only so many (Apache's `MaxRequestWorkers`, php-fpm's `pm.max_children`, a shared host's process limit). **The pool has to be larger than workers and waiters together** (six by default), or an overload of the API takes every PHP worker and the rest of the site queues behind it in the web server, where nothing of this host's can refuse anything. Measured behind an Apache with a capped pool (prefork, PHP run as CGI, so that a static file needs one of the same workers), 40 requests a second for ten seconds (twice what four workers serve), with a static file and another PHP page of the same site fetched meanwhile: on a pool of eight or sixteen both stayed at 1 ms and 15 ms, as they were with no waiting, and the API served as many as before and refused the rest in 18 ms; on a pool of five (one more than the workers; Ubuntu's php-fpm package ships `pm.max_children = 5`) every request took three to seven seconds, the static file and the other page included, where with no waiting those two had taken 7 and 21 ms, and `"slotWaiters": 0` put that back. The same happened to a pool of eight with eight allowed to wait. So on a pool that is not larger than workers plus waiters, set `slotWaiters` to 0 or lower the workers (`"workers"` in `private/config.json`, which holds the manifest's `config.server.workers` to it and outlasts an update of the app). Where the pool is large enough, the overload holds at most workers plus waiters of it (at most nine PHP workers busy at once at 40 and at 100 requests a second, where refusing at once held five to thirteen), and the requests that are served take a third of a second at the median where they took a quarter.

**Under php-fpm no request waits by itself.** A request past the slots is told at once that the server is busy, as before there was any waiting, until the operator writes `"slotWaiters"`. php-fpm's own pool is the small one: five children as Ubuntu's package ships it (`pm.max_children = 5`), one more than the default four workers. Measured on php-fpm 8.3.6 behind Apache (mod_proxy_fcgi), with the same overload: on a pool of five, with two allowed to wait, every PHP page of the site took three seconds at the median and up to seven (a static file, which the web server sends itself, 0.04 to 0.2 s), on the package's own settings (`pm = dynamic`, at most 5) as on `pm = static`; with nobody waiting a page takes 1 ms through the overload on the static pool and the API refuses in 2 ms, which is what this host answers there now, to the millisecond what it answered before. With a pool that has room, the operator says so: `"slotWaiters": 2` on a pool of sixteen answered five of five and six of six calls made together (a third of a second) and kept a PHP page at 1 ms through the overload; the same number on the pool of five is the three seconds again, because a number written there is taken at its word, under php-fpm too. So under php-fpm write `slotWaiters` only for a `pm.max_children` larger than workers plus that number. (On the package's dynamic pool a burst is answered either way, five and twelve calls alike, since php-fpm starts with two children and holds the rest of a burst in its own queue; it is the steady overload that tells the settings apart.)

The host cannot decide this for itself there, though php-fpm has the means. `fpm_get_status()` reports how many of the pool's processes are idle, and waiting only while one is would fit any pool; `softn_pool_has_room` in request.php reads its answer that way, and is tested. But calling it could not be trusted where it was tried. That was php-fpm 8.3.6, the binary of Ubuntu 24.04's package unpacked and run as a user (not installed: no php.ini, not under systemd), static pools on a unix socket behind Apache. A page that does nothing but call `fpm_get_status()` ended its child with SIGSEGV when requests asked for it together, in some runs and not in others: never in 200 requests made one at a time, 9 times in 60 made two at a time, once in 120 and never in another 360 made twelve at a time. This host's own requests did the same when they called it: in two bursts of twelve, two each were answered by Apache's 503, their php-fpm child gone. What sets it off was not found. So http.php hands that function no status and never makes the call; it is one line to change on a php-fpm where the call can be trusted.

Optional operator/after-request.mjs runs only when private configuration explicitly sets enableAfterRequestHook:true. This is privileged, operator-installed integration code, not sandboxed application logic. It can perform bounded delivery/retry work after the guest transaction. It is never selected by a request or the manifest. Operator defaults can supply configuration via operator/defaults.json. Do not install untrusted operator modules. Applications without these adapters need none of this folder.

The runner also has an independent 20-second deadline on its supervising Node thread. WASM and synchronous SQLite run in a worker thread; a stuck worker cannot block the supervisor, which ends the process with a signal rather than an exit that would wait for a worker inside a statement that never finishes. This bounds execution even if the PHP parent disappears, and the runner does not inherit the request's slot lock. The outer PHP deadline remains a second safeguard. A migration the deadline stops is rolled back and named in the log (`softn: startup stage database_migrations: migration 002.sql was stopped at the 20 s deadline (1 of 3)`), and noted in `private/data/migration-stopped.json`; after three stops it is not started again, and requests answer `diagnostic:"migration_stopped"` at once, until the migration's file changes or that note is removed. `php backend/setup.php --migration-deadline=SECONDS` applies a migration that needs longer (Startup diagnostics, below). Only the runner's own deadline counts a stop: a runner that PHP or the machine ended, and a request that only waited for the write lock, leave no note. Pending migrations run in one transaction, so several that together take longer than the deadline are stopped as well, and the one named is the one that was running. It used to be started again by every request, each holding a process slot and the write lock for 20 seconds, with nothing in the log.

No background work runs while a site is idle. Integrations needing guaranteed retries should use an operator cron tick or another supported delivery system. Preserve private/config.json and private/data/ across updates; never publish them. Do not swap app IDs under an existing configuration. Existing native databases/keys require an explicit migration, not an automatic import.

This is a tested preview, not an independent security audit or a claim of compatibility with every native-server feature. Keep PHP, Node and ZIPP patched. The engine and host adapter form the trust boundary; PHP process launching alone is not a sandbox.

## Trusted request integrations

Private configuration can opt into `enableRequestHook:true`; requests then run on Node, which alone runs the hook (softn-runner, above, refuses it). The host then loads the fixed operator-installed `operator/request.mjs` and calls its async `handleRequest({request,route,invoke,db,crypto,config})` for declared routes after migrations and host rate admission. A missing or failing enabled hook fails closed. `invoke(context)` executes the original request in the normal WASM transaction with a separate trusted `request.context`; any client-supplied context is discarded, including when the hook is disabled. The default context is empty. This supports bounded provider checks outside the guest and outside SQL transactions. The existing 20-second supervisor and 25-second PHP deadlines still apply.

The hook is privileged operator code with database and host access, not a guest capability or manifest-selected extension. Only install trusted integrations. Keep provider credentials in private configuration; pass only necessary validated results into context. Apps without this setting retain the normal route invocation. The after-request hook remains a separate opt-in.

## Startup diagnostics

What a client is told and what the operator can read are kept apart. A request that fails writes to PHP's error log (`error_log`, wherever the server sends it) and nowhere else: one line per failure, `softn-host <METHOD> <path>: softn: handler <name>: <reason>` for a handler that threw, returned something that is not a response, or made a host call that failed; `softn: startup stage <stage>: <reason>` for a start that failed; and `softn: runner <step>` when the runner's process could not be started, timed out, or did not answer in the host's protocol. The reason is the exception's own message, cut at 300 characters, with control characters removed and anything shaped like a file path replaced by `<path>`: it can name a table or a column, and it can carry whatever text an app puts in an error it throws, so treat the log as you treat the database. Never a stack, a bind value, a key or a path. A request that succeeds logs nothing, and so does a database that was only busy.

A `runner_unavailable` response carries a `diagnostic` naming the step that failed (`spawn`, `timeout`, `write`, `read`, `output_limit`, `runner_failure`, `protocol`, `request_encoding`), and nothing else about it.

A `backend_unavailable` response includes a static `diagnostic` label identifying the failed startup stage, such as `configuration_read`, `application_identity`, `database_migrations`, or `wasm_initialization`. Those are the runner's stages. `migration_stopped` is one more: a migration ran until the runner's 20-second deadline three times and is no longer started, so the app stays down until someone acts. The log and `php backend/setup.php` name the file. Make the migration finish in time (smaller steps, deployed a release at a time, since pending migrations share one transaction) or, once whatever slowed it has passed, remove `private/data/migration-stopped.json` to have it tried again. A migration that needs longer than the 20 seconds is applied by setup: `php backend/setup.php --migration-deadline=SECONDS` (1 to 86400) gives that run's check of the app that long, starts a migration stopped three times all the same, and removes the note once the migration is in. Only that run has the longer deadline (setup passes it to the runner it starts, and http.php starts the runner with an environment of its own); requests keep their 20 seconds, and while the migration runs they wait for the database and may be answered `503 database_busy`. Before this option such a migration could never be applied, since setup's own check ran under the same deadline. It used to be answered as `database_migrations`, the label of a migration that failed or does not match the ledger, with the reason in the log alone. PHP's own, answered before a runner is started, name what the installation lacks: `php_version`, `backend_path`, `open_basedir`, `php_process_functions`, `backend_public`, `private_permissions` (`private/`, or the slot files in it, cannot be opened by the account the web server runs PHP as; this used to be `setup_required`, or "the server is busy" for ever), `setup_required` and `php_gd`. `php backend/setup.php` prints the runner's reason beside the stage label, which a response never carries. It never includes raw exceptions, configuration values, SQL, keys, tokens, or filesystem paths. This label narrows investigation; it does not establish the underlying cause. Preserve private configuration and data while diagnosing an existing deployment.
